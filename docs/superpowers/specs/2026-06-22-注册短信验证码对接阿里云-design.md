# 注册手机验证码对接阿里云短信 — 设计方案

- 日期：2026-06-22
- 状态：已与用户确认设计方向，经多智能体自检 + Redis/内存取舍二次确认，待最终评审
- 范围：把"用户注册手机验证码"从硬编码 `888888` 改为真实的阿里云短信下发 + **进程内内存**存储 + 校验链路，含前端输入限制与防刷。
- 备注：关键修订项见第 17 节"自检修订记录"。**存储已从 Redis 改为进程内内存**（理由见第 2、13 节）。

## 1. 背景与现状

经代码探查确认当前实现：

- **无真实短信链路**：验证码前后端均硬编码为 `888888`。
  - 后端常量 `FIXED_REGISTER_CODE = "888888"`（`AuthService.java:40`），注册时直接字符串比较（`AuthService.java:82`）。
  - 前端 `Login.vue` 默认 `code: '888888'`（`Login.vue:138`），`handleRegister` 提交时带上 `registerForm.code`（`:206-211`），且第 202 行有 `if (!registerForm.phone || !registerForm.code || !registerForm.password) return` 的**非空守卫**。
- **无发送验证码接口**：仅有 `POST /api/v1/auth/register` 与 `POST /api/v1/auth/login`。
- **register 已有重复手机号检查**：`AuthService.register` 先 `selectCount` 查重复（`:89-93`，409），并对 `DuplicateKeyException` 兜底（`:106-108`）。但目前**在验证码校验之后**才查。
- **无 Redis、且项目刻意规避 Redis**：`pom.xml:361-364` 明确 ShedLock 用 JDBC 模式"so there is no Redis dependency on the desktop / single-node footprint"——项目有**桌面/单机部署形态**并主动不引入 Redis。现有限流用 Caffeine 本地缓存（`LoginRateLimitFilter`）。
- **限流现状**：`LoginRateLimitFilter` 受限端点是**硬编码** `AUTH_PATHS = Set.of("/api/v1/auth/login","/api/v1/auth/register")`（`:27-30`），阈值 `MAX_ATTEMPTS = 5`（`:26`），对 POST 且 requestURI 精确相等才计数（`:43`）。取客户端 IP 走 `X-Forwarded-For` 首段 → `X-Real-IP` → `getRemoteAddr()`（`:62-72`）。
- **无任何阿里云短信 SDK**：所有 pom 中只有 DashScope（AI 用），没有 dysmsapi。Caffeine（`com.github.ben-manes.caffeine:caffeine`）已是依赖。
- **配置**：`application.yml` + 环境变量（`${VAR:default}`）注入。前缀**两套并存**：`mateclaw.*`（jwt/mcp/skill/llm）与 `mate.*`（agent/wiki/memory）。`@ConfigurationProperties` 类**统一靠显式 `@EnableConfigurationProperties` 注册**（如 `MemoryAutoConfiguration`），全项目**无** `@ConfigurationPropertiesScan`。
- **手机号校验**：正则 `PHONE_PATTERN = ^\+?\d{6,20}$` 是 `AuthService` 的 `private static final`（`:41`），且校验在 `normalizePhone()`（去空格/连字符，`:319-324`）**之后**才 match（先 normalize 再 match，`:78-79`）。
- **异常体系**：`MateClawException(msgKey, httpStatus, message)` 可表达任意 HTTP 状态（含 429）。
- **测试**：`AuthServiceRegisterTest` 是 `@ExtendWith(MockitoExtension.class)` 纯 Mockito 单测，`@InjectMocks` 构造 `AuthService` + 4 个 `@Mock`（UserMapper / BCryptPasswordEncoder / WorkspaceService / AccountEntitlementService），用 `ReflectionTestUtils.setField` 注入 jwt 字段，**不加载 Spring 上下文**；`AuthControllerRegisterTest` 直接 `new AuthController(authService, entitlementService)`。仓库**无** `application-test.yml`。验证码在测试里写死 `888888`。surefire 已配置 byte-buddy 静态 agent（Mockito on JDK 21）。

## 2. 已确认的关键决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 验证码存储 | **进程内内存**（`ConcurrentHashMap` + 注入 `Clock`） | 项目刻意规避 Redis 保桌面/单机形态（`pom.xml:361-364`）；多实例约束见第 13 节 |
| 凭据配置 | **全局环境变量**（签名/模板写 yml） | 与 `JWT_SECRET` 一致；全平台统一一个阿里云账号 |
| 开发/测试旁路 | **配置开关 `mock` + 万能码** | dev/集成不真发、不耗配额（口径见第 7 节） |
| 防刷强度 | **多维限流**（同号间隔 + 单号/单 IP 滚动 24h 上限 + 全局每分钟熔断） | 挡住滥用、保护账单，不引入图形验证码 |

固定业务参数（用户给定）：

- 短信签名：`迪伍科技`
- 短信模板：`SMS_508735089`
- 模板变量：`code`
- 验证码：**固定 6 位数字**（`code-length` 固化为常量 6，不做可配项，避免前后端口径冲突）

> 🔒 阿里云 AccessKeyId / AccessKeySecret 仅通过环境变量注入，**绝不写入任何受版本控制的文件**。用户提供的密钥需在阿里云控制台轮换，并**要求**改用仅含 `dysmsapi:SendSms` 权限的 RAM 子账号；dev 与 prod 使用不同子账号密钥以隔离爆炸半径。

## 3. 总体架构

新增一条真实"发送 → 存储 → 校验"链路替换硬编码。核心拆成职责单一、可独立测试的单元：

| 单元 | 职责 | 依赖 |
|------|------|------|
| `PhoneNumbers`（工具类） | 抽取现有 `PHONE_PATTERN` + `normalize`，供注册与发码端点**共用同一口径** | — |
| `SmsCodeSender`（接口） | 把验证码发送到手机号；屏蔽具体服务商 | — |
| ├ `AliyunSmsCodeSender`（`mock=false` 装配） | 调用阿里云 dysmsapi 真实发送 | 阿里云 SDK |
| └ `MockSmsCodeSender`（`mock=true` 装配） | 不真发，仅非生产日志打印 | — |
| `VerificationCodeStore`（接口） | 验证码 + 各限流计数器/锁的**原子**存取与过期 | — |
| └ `InMemoryVerificationCodeStore` | 唯一实现：`ConcurrentHashMap` + 注入 `Clock`，`compute` 保证单 key 原子，`@Scheduled` 清扫过期桶 | — |
| `VerificationCodeService` | 生成 6 位码、防刷限流、校验、一次性消费、mock 旁路 | 上面接口 + `SmsProperties` |
| `SmsProperties` | `@ConfigurationProperties("mateclaw.sms")`，**必须**在 sms 配置类上 `@EnableConfigurationProperties(SmsProperties.class)` 显式注册（项目无 scan） | — |
| `SmsStartupValidator` | 启动期硬校验：见第 7/11 节 fast-fail | `SmsProperties`、Environment |
| `AuthController.sendRegisterCode` | 新增 HTTP 端点 | `VerificationCodeService` |

**设计意图**：
- "发送""存储"抽象成接口 → 单测可注入 fake clock 与内存实现跑通全链路；服务商将来可替换。
- `AliyunSmsCodeSender` / `MockSmsCodeSender` 通过 `@ConditionalOnProperty(mateclaw.sms.mock)` **在装配层二选一**，使生产环境根本不装配 Mock 实现（纵深防御，而非仅运行期 if）。
- 前缀统一用 `mateclaw.sms`（与 `mateclaw.jwt` 对齐），**勿照 `mate.memory` 误写成 `mate.sms`**。

## 4. 接口设计

### 4.1 新增：发送注册验证码

`POST /api/v1/auth/send-register-code`，请求 `{ "phone": "13800138000" }`

流程（**关键：先原子占位，再发送，失败回退**，杜绝并发绕过）：

1. 用 `PhoneNumbers.normalize` + `PHONE_PATTERN` 校验（与注册**完全相同**的 normalize+正则口径）。
2. **已注册检查**：`userMapper.selectCount(username=phone) > 0` → 返回"该手机号已注册，请直接登录"（账号枚举为注册端点固有、行业通行，列为已接受残余风险，见第 13 节）。
3. **原子抢占重发锁**：`store.tryAcquireSendLock(phone, resendInterval)`。失败（锁存在且未过期）→ 立即 429，提示剩余等待秒数。**此步先于发送**，关闭"发送中窗口被并发绕过"的缺口。
4. **原子占用限流额度**：依次 `incrementWindow` 三个计数（任一超限即回退已占额度 + `releaseSendLock` → 429）：
   - `daily:phone:{phone}`（滚动 24h，上限 `daily-limit-per-phone`）
   - `daily:ip:{ip}`（滚动 24h，上限 `daily-limit-per-ip`）
   - `global`（滚动 60s，上限 `global-limit-per-minute`）
5. 用 `SecureRandom` 生成 6 位数字码（含前导零，等概率），`store.putCode(phone, code, codeTtl)`（覆盖写、attempts 归零、刷新过期）。
6. 调 `SmsCodeSender.send(phone, code)`，模板参数 `{"code": code}`。
7. **发送成功** → 返回 `{ "success": true }`（不含验证码明文）。
8. **发送失败** → `store.removeCode(phone)`、`decrementWindow` 回退第 4 步三个计数、`store.overwriteSendLock(phone, failureCooldown)`（把 60s 锁改写为较短失败冷却，失败可重试但**非无间隔无限重试**）；记录阿里云 `Code/Message/bizId` 到日志；返回 502/通用错误。

### 4.2 改造：注册校验

`POST /api/v1/auth/register`（`AuthService.register`），改造后顺序：

1. `phone = PhoneNumbers.normalize(...)`；格式非法 → 400（同现状）。
2. `password` 非空校验（同现状）。
3. **重复手机号检查前移到验证码消费之前**（现 `:89-93` 的 `selectCount` 检查上移）：已注册 → 409，**不消费验证码**。避免为注定失败的注册白消耗码。
4. `verificationCodeService.verifyAndConsume(phone, code)`：内部 `store.verifyAndConsume` **原子**完成"查码→比对→命中即删除并返回 / 未命中则 `attempts++` 并按返回判断是否超 `max-verify-attempts`（超则作废码）"；不存在/过期 → "验证码已失效"；超次数 → "错误次数过多，请重新获取"。verify 失败对 `phone` 施加 `verify-fail` 滚动 60s 窗口限流，防枚举。
5. 继续现有建用户（`insert` + `DuplicateKeyException` 兜底）、建工作区、发 token 逻辑。
6. **一次性消费与注册业务一致性**：`verifyAndConsume` 成功后码即删除。**若第 5 步任一步骤失败**：捕获后**补偿性 `store.releaseSendLock(phone)`**，使用户可立即重新获取验证码，不被 60s 间隔锁死（日上限仍适用）。

## 5. 数据存储（进程内内存）

不引入 Redis。`InMemoryVerificationCodeStore` 用 `ConcurrentHashMap` + 注入的 `java.time.Clock`（生产 `Clock.systemUTC()`，测试用可推进的 fixed/mutable clock）实现；所有"检查+占用"通过 `ConcurrentHashMap.compute` 保证**单 key 原子**；`@Scheduled` 每数分钟清扫过期桶以界定内存。

| 逻辑条目 | 结构 | 过期 | 用途 |
|----------|------|------|------|
| code | `Map<phone, CodeEntry{ String code; int attempts; long expiresAtMs }>` | `code-ttl-seconds`（300s） | 验证码 + 错误次数同条目，原子过期 |
| sendLock | `Map<phone, long blockedUntilMs>` | 正常 60s / 失败 10s | 重发/失败冷却锁，`compute` 原子抢占 |
| daily:phone:{phone} | `Map<key, Window{ long startMs; int count }>` | 滚动 24h | 单手机号上限（默认 10） |
| daily:ip:{ip} | 同上 | 滚动 24h | 单 IP 上限（默认 30） |
| global | 同上（单 key） | 滚动 60s | 全局每分钟总量熔断（默认 200） |
| verifyfail:{phone} | 同上 | 滚动 60s | verify 失败速率限制，防枚举 |

**滚动窗口**：`Window` 在首次自增时锚定 `startMs`；`now - startMs >= window` 则重置为新窗口。这刻意**取代日历日 + 时区**方案，消除自检发现的跨天/时区边界问题。

接口方法（实现均以 `compute` 原子化）：
- `boolean tryAcquireSendLock(String phone, Duration ttl)` — 锁不存在/已过期则占用返回 true，否则 false。
- `void overwriteSendLock(String phone, Duration ttl)` / `void releaseSendLock(String phone)`
- `long incrementWindow(String key, Duration window)` 返回自增后计数 / `void decrementWindow(String key, Duration window)` 回退
- `void putCode(String phone, String code, Duration ttl)` — 覆盖、attempts 归零、刷新过期
- `void removeCode(String phone)`
- `VerifyOutcome verifyAndConsume(String phone, String code, int maxAttempts)` — 原子返回 `OK`（并删除）/`MISMATCH`（attempts++）/`EXPIRED`（含 not-found）/`TOO_MANY`（删除）

## 6. 防刷设计（多维限流）

发送前按"原子占位"顺序检查，命中任一即 429：

1. **同号间隔锁**（默认 60s）：`tryAcquireSendLock`，抢占失败即拒。
2. **单手机号滚动 24h 上限**（默认 10）：`incrementWindow` 超限回退。
3. **单 IP 滚动 24h 上限**（默认 30）：同上。
4. **全局每分钟总量熔断**（默认 200/分钟）：最终保护阿里云配额/账单，挡住"多号×多 IP 矩阵"线性放大。
5. **复用现有 IP/分钟级限流**：将 `/api/v1/auth/send-register-code` 加入 `LoginRateLimitFilter.AUTH_PATHS`（硬编码 Set，改源码加一行精确 URI；阈值 `MAX_ATTEMPTS=5` 硬编码）。该 filter 与上述内存多维限流是**两套独立计数、不共享**。

**客户端 IP 来源**：取 IP 复用 `LoginRateLimitFilter.getClientIp` 同一策略（XFF 首段 → X-Real-IP → remoteAddr）。注意：该策略**信任 XFF 头**，在无可信代理收敛时 XFF 可被伪造从而绕过 IP 维度限流——这是现状既有风险，本次沿用并在第 13 节列为已知残余风险（单号上限与全局熔断仍兜底）。

不引入图形/滑块验证码（按已确认决策）。

## 7. 测试旁路（mock + 万能码）

配置开关 `mateclaw.sms.mock`，**默认 fail-safe = `false`**（`${SMS_MOCK:false}`，"忘配=安全"）：

- **`mock=true`（本地开发/集成测试显式开启）**：
  - 装配 `MockSmsCodeSender`：不调用阿里云，仅**非生产**日志打印手机号与码。
  - `VerificationCodeService.verifyAndConsume` 在正常校验之外，**额外接受配置的 `universal-code`（默认 888888）**，用于 dev 联调与 `@SpringBootTest` 集成测试免发短信。
- **`mock=false`（生产）**：
  - 装配 `AliyunSmsCodeSender` 真实发送；`MockSmsCodeSender` 与万能码逻辑在装配层即不可达。
- **启动期硬校验 `SmsStartupValidator`**：active profile 含 `prod` 时强制 `mock=false`，否则**启动失败（fast-fail）**；`mock=false` 且 AK/SK 为空亦 fast-fail；`mock=true` 时打印显著启动告警。

> ⚠️ **修订**：原 spec 称"现有写死 888888 的注册单测无需改动即通过"——**不成立**。`AuthServiceRegisterTest`/`AuthControllerRegisterTest` 是纯 Mockito 单测、无 Spring 上下文；`register()` 改为委托 `verificationCodeService.verifyAndConsume()` 后，这些测试必须**新增 `@Mock VerificationCodeService` 并 stub**（否则编译可过但运行 NPE）。万能码属 `VerificationCodeService` 内部逻辑，对纯单测不可见；它只服务于本地联调与集成测试。测试改动见第 12 节。

## 10. 前端改造（Login.vue）

- **验证码输入框（`:58-69`）：只允许 6 位数字** —— `maxlength="6"`，`@input` 剥离非数字并截断 6 位；提交前校验恰好 6 位数字。
- 在验证码输入框旁加"获取验证码"按钮：点击调 `authApi.sendRegisterCode({ phone })`，成功后启动 **60s 倒计时**并禁用按钮（`ref` 计时器）。
- 移除 `registerForm` 的 `code: '888888'` 默认值（`:138` 改为 `code: ''`）；确保获取验证码后用户输入回填 `registerForm.code`，否则 `handleRegister` 第 202 行 `!registerForm.code` 守卫会让提交**静默不发请求**。
- `@/api/index` 的 `authApi` 增加 `sendRegisterCode(payload)`（参照现有 `register`/`login`）。
- 错误处理：限流 429 → toast 友好提示（含可重试时间）；发送失败 → 通用提示；已注册 → 引导去登录。i18n key 复用现有 `login.*` 命名（用 `grep "login.placeholders.code"` 定位 locale 文件并补键）。

## 11. 错误处理

| 场景 | HTTP | 行为 |
|------|------|------|
| 手机号格式非法 | 400 | 复用现有异常体系（与注册同一 normalize+正则口径） |
| 手机号已注册 | 409 | 引导去登录（残余枚举风险见第 13 节） |
| 重发/失败冷却内 / 各维度上限 / 全局熔断 | 429 | 友好提示，含可重试时间 |
| 阿里云发送失败 | 502 | 记录 `Code/Message/bizId`；删码、回退计数、改设失败冷却锁；返回通用错误 |
| 验证码错误 | 400 | 原子累加次数；超 `max-verify-attempts` 作废并提示重新获取 |
| 验证码过期/不存在 | 400 | "验证码已失效，请重新获取" |
| 启动校验失败（prod 且 mock=true，或 mock=false 但 AK/SK 为空） | — | **fast-fail 启动失败**，拒绝带病上线 |

对外文案不泄露验证码与内部细节；阿里云原始错误码仅入日志且确认不含码。

## 13. 安全设计小结

- **凭据**：AK/SK 仅环境变量，禁止入库；要求 RAM 子账号（仅 `dysmsapi:SendSms`）；dev/prod 不同子账号；用户已暴露密钥需立即轮换。`mock=false` 且 AK/SK 空 → 启动 fast-fail。
- **万能码 fail-safe**：默认 `mock=false`；装配层 + 启动校验双重保证生产不可达；CI 断言 `mock=false` 拒万能码。
- **验证码随机性**：强制 `SecureRandom`。
- **不泄露码**：响应不含码；mock 打印码仅限非生产；审计日志点不含真实码。
- **防枚举/轰炸**：原子"先占位"限流；`verify-fail` 速率限制；全局每分钟熔断保账单。
- **⚠️ 多实例约束（内存存储固有，重点）**：验证码与所有限流计数**仅在单实例进程内有效**。多实例**非粘性**部署会导致：(1) A 实例下发的码在 B 实例校验为 `EXPIRED`（注册失败）；(2) 各实例限流独立、总量翻 N 倍。**因此注册功能要求单实例或会话粘性（sticky session）路由**，与项目桌面/单机形态一致。列为已知运维约束，需在部署文档明示；若未来要多实例无粘性，须改回共享存储（Redis/DB）。
- **已接受残余风险**：注册端点固有的"手机号是否可注册"枚举（限流+监控缓解）；`X-Forwarded-For` 可伪造导致 IP 维度限流被绕过（单号上限+全局熔断兜底，现状既有）。

## 14. 不在本次范围（YAGNI）

- 工作区级独立短信账号/签名（当前全平台统一账号）。
- 图形/滑块验证码。
- 登录、找回密码等其他短信场景（仅做注册）。
- 短信发送审计持久化表。
- 多实例共享存储（Redis/DB）——本次明确单实例/粘性。
- 独立的 `verifyfail:{phone}` 校验失败滚动窗口（§5 曾列出）——实现时**合并进单码 `max-verify-attempts=5` 上限**：每个码至多 5 次错误即作废，配合发送侧限流已足够界定枚举速率，不再单设计数器。

## 15. 验收标准

1. 生产配置（`mock=false`）下，注册页点击"获取验证码"能收到来自"迪伍科技"签名、模板 `SMS_508735089` 的 6 位数字短信。
2. 输入正确验证码可注册成功；错误/过期/超次数/已注册按第 11 节返回对应错误。
3. 同号间隔内重发被拒；单号/单 IP 滚动 24h 上限、全局每分钟熔断生效；并发请求不超发。
4. dev/集成（`mock=true`）下不真实发短信；现有测试经第 12 节改动后全绿。
5. 仓库内无任何明文 AccessKey/Secret；凭据全部来自环境变量；不引入 Redis 依赖。
6. prod 且 mock=true，或 mock=false 但密钥为空时，应用启动 fast-fail。
