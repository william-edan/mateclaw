# 注册手机验证码对接阿里云短信 — 设计方案

- 日期：2026-06-22
- 状态：已与用户确认设计方向，并经多智能体对抗式自检修订，待 spec 评审
- 范围：把"用户注册手机验证码"从硬编码 `888888` 改为真实的阿里云短信下发 + Redis 存储 + 校验链路，含前端输入限制与防刷。
- 备注：本文档第 3~14 节已根据自检结论修订，关键修订项在第 17 节"自检修订记录"列出。

## 1. 背景与现状

经代码探查确认当前实现：

- **无真实短信链路**：验证码前后端均硬编码为 `888888`。
  - 后端常量 `FIXED_REGISTER_CODE = "888888"`（`AuthService.java:37`），注册时直接字符串比较（`AuthService.java:82`）。
  - 前端 `Login.vue` 默认 `code: '888888'`（`Login.vue:138`），`handleRegister` 提交时带上 `registerForm.code`（`:207-208`），且第 202 行有 `if(!registerForm.code) return` 的**非空守卫**。
- **无发送验证码接口**：仅有 `POST /api/v1/auth/register` 与 `POST /api/v1/auth/login`。
- **无 Redis、无验证码存储**：限流用 Caffeine 本地缓存（`LoginRateLimitFilter`）。受限端点是**硬编码** `AUTH_PATHS = Set.of(...)`（`:27-30`），阈值 `MAX_ATTEMPTS = 5`（`:26`）也是硬编码常量，对 POST 且 requestURI 精确相等才计数（`:43`）。手机号维度的发送频率限制不存在。
- **无任何阿里云短信 SDK**：所有 pom 中只有 DashScope（AI 用），没有 dysmsapi。
- **配置**：`application.yml` + 环境变量（`${VAR:default}`）注入。前缀**两套并存**：`mateclaw.*`（jwt/mcp/skill/llm）与 `mate.*`（agent/wiki/memory）。`@ConfigurationProperties` 类**统一靠显式 `@EnableConfigurationProperties` 注册**（如 `MemoryAutoConfiguration`、`LlmCacheAutoConfiguration`），全项目**无** `@ConfigurationPropertiesScan`。
- **手机号校验**：正则 `PHONE_PATTERN = ^\+?\d{6,20}$` 是 `AuthService` 的 `private static final`（`:41`），且校验在 `normalizePhone()`（去空格/连字符，`:319-324`）**之后**才 match（先 normalize 再 match，`:78-79`）。
- **异常体系**：`MateClawException(messageKey, httpStatus, defaultMessage)` 可表达任意 HTTP 状态（含 429）。
- **测试**：`AuthServiceRegisterTest` 是 `@ExtendWith(MockitoExtension.class)` 纯 Mockito 单测，用 `@InjectMocks` 构造 `AuthService` + 4 个 `@Mock`（UserMapper / BCryptPasswordEncoder / WorkspaceService / AccountEntitlementService），**不加载 Spring 上下文**；`AuthControllerRegisterTest` 直接 `new AuthController(...)`。仓库**无** `application-test.yml`。验证码在测试里写死 `888888`。

## 2. 已确认的关键决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 验证码存储 | **Redis** | 多实例共享、重启不丢、原子化频率/次数控制 |
| 凭据配置 | **全局环境变量**（签名/模板写 yml） | 与 `JWT_SECRET` 一致；全平台统一一个阿里云账号 |
| 开发/测试旁路 | **配置开关 `mock` + 万能码** | dev/集成不真发、不耗配额（详见第 7 节修订后口径） |
| 防刷强度 | **多维限流**（同号间隔 + 单号日上限 + 单 IP 日上限 + 全局总量熔断） | 挡住滥用、保护账单，不引入图形验证码 |

固定业务参数（用户给定）：

- 短信签名：`迪伍科技`
- 短信模板：`SMS_508735089`
- 模板变量：`code`
- 验证码：**固定 6 位数字**（见第 8 节：`code-length` 不做成可配项，固化为常量 6，避免前后端口径冲突）

> 🔒 阿里云 AccessKeyId / AccessKeySecret 仅通过环境变量注入，**绝不写入任何受版本控制的文件**。用户提供的密钥需在阿里云控制台轮换，并**要求**改用仅含短信发送（dysmsapi:SendSms）权限的 RAM 子账号，dev 与 prod 使用不同子账号密钥以隔离爆炸半径。

## 3. 总体架构

新增一条真实"发送 → 存储 → 校验"链路替换硬编码。核心拆成职责单一、可独立测试的单元：

| 单元 | 职责 | 依赖 |
|------|------|------|
| `PhoneNumbers`（工具类） | 抽取现有 `PHONE_PATTERN` + `normalizePhone`，供注册与发码端点**共用同一口径** | — |
| `SmsCodeSender`（接口） | 把验证码发送到手机号；屏蔽具体服务商 | — |
| ├ `AliyunSmsCodeSender`（`mock=false` 装配） | 调用阿里云 dysmsapi 真实发送 | 阿里云 SDK |
| └ `MockSmsCodeSender`（`mock=true` 装配） | 不真发，仅日志打印（仅限非生产） | — |
| `VerificationCodeStore`（接口） | 验证码值/错误次数/各限流计数器的原子存取与 TTL | — |
| ├ `RedisVerificationCodeStore` | 生产实现，限流原子操作用 Lua 脚本 | Redis |
| └ `InMemoryVerificationCodeStore` | 单测实现，无需 Redis 基础设施 | — |
| `VerificationCodeService` | 生成 6 位码、防刷限流、校验、一次性消费、mock 旁路 | 上面接口 + `SmsProperties` |
| `SmsProperties` | `@ConfigurationProperties("mateclaw.sms")`，**必须**在 sms 配置类上 `@EnableConfigurationProperties(SmsProperties.class)` 显式注册（项目无 scan） | — |
| `SmsStartupValidator` | 启动期硬校验：见第 7/11 节 fast-fail | `SmsProperties`、Environment |
| `AuthController.sendRegisterCode` | 新增 HTTP 端点 | `VerificationCodeService` |

**设计意图**：
- "发送""存储"抽象成接口 → 单测用内存实现跑通全链路，不依赖 Redis 与真实短信；服务商/存储可替换。
- `AliyunSmsCodeSender` / `MockSmsCodeSender` 通过 `@ConditionalOnProperty(mateclaw.sms.mock)` **在装配层二选一**，使生产环境根本不装配 Mock 实现（纵深防御，而非仅运行期 if）。
- 前缀统一用 `mateclaw.sms`（与 `mateclaw.jwt` 对齐），**勿照 `mate.memory` 误写成 `mate.sms`**。

## 4. 接口设计

### 4.1 新增：发送注册验证码

`POST /api/v1/auth/send-register-code`，请求 `{ "phone": "13800138000" }`

流程（**关键：先原子占位，再发送，失败回退**，杜绝并发绕过）：

1. 用 `PhoneNumbers.normalize` + `PHONE_PATTERN` 校验（与注册**完全相同**的 normalize+正则口径）。
2. **已注册检查**：手机号若已注册 → 返回"该手机号已注册，请直接登录"（账号枚举为注册端点固有、行业通行，列为已接受残余风险并以限流+监控缓解，见第 13 节）。
3. **原子抢占重发锁**：`SET sms:reg:resend:{phone} 1 NX EX 60`。失败（锁已存在）→ 立即 429，提示剩余等待秒数。**此步先于发送**，关闭"发送中窗口被并发绕过"的缺口。
4. **原子占用日额度**：对 `daily:phone` 与 `daily:ip` 与 `global`（见第 5/6 节）用 Lua 脚本 `INCR + 首次设 EXPIRE + 判断是否超限`；任一超限 → 回退已占额度 + 删除第 3 步重发锁 → 429。
5. 用 `SecureRandom` 生成 6 位数字码（含前导零，等概率），原子写入 `sms:reg:code:{phone}`（Hash `{code, attempts=0}`，`EXPIRE = code-ttl-seconds`，用单条 Lua/HSET+EXPIRE 保证"写码+清零+设 TTL"原子）。
6. 调 `SmsCodeSender.send(phone, code)`，模板参数 `{"code": code}`。
7. **发送成功** → 返回 `{ "success": true }`（不含验证码明文）。
8. **发送失败** → 删除第 5 步的码、回退第 4 步日额度；将第 3 步的 60s 重发锁**改写为一个较短的失败冷却锁**（如 `EX failure-cooldown-seconds`，默认 10s），即失败可重试但**不是无间隔无限重试**；记录阿里云 `Code/Message/bizId` 到日志；返回 502/通用错误。

### 4.2 改造：注册校验

`POST /api/v1/auth/register`（`AuthService.register`）

- `AuthService` 新增构造器依赖 `VerificationCodeService`（`@RequiredArgsConstructor`）。
- 删除 `FIXED_REGISTER_CODE` 常量与字符串比较，改为：
  1. **再次已注册检查**（防 send 到 register 之间状态变化），已注册 → 拒绝且不消费码。
  2. `verificationCodeService.verifyAndConsume(phone, code)`：用 **Lua 脚本原子**完成"查码→比对→命中即 DEL 返回成功 / 未命中则 `HINCRBY attempts` 并按返回值判断是否超 `max-verify-attempts`（超则作废码）"。不存在/过期 → "验证码已失效"；超次数 → "错误次数过多，请重新获取"。原子化杜绝并发枚举绕过阈值。
  3. 为防枚举，verify 失败对 `phone` 维度施加独立的失败速率限制（短窗口计数）。
- **一次性消费与注册业务的一致性**：`verifyAndConsume` 成功（码已删）后继续现有建用户/建工作区/发 token 逻辑。**若后续任一步骤失败**：捕获异常后**补偿性删除该手机号的重发锁/失败冷却锁**，使用户可立即重新获取验证码，不被 60s 间隔锁死（日上限仍适用）。spec 明确该失败窗口与可恢复手段。

## 5. 数据存储（Redis key 设计）

| key | 类型/值 | TTL | 用途 |
|-----|---------|-----|------|
| `sms:reg:code:{phone}` | Hash `{ code, attempts }` | `code-ttl-seconds`（300s） | 验证码 + 错误次数共享同一 TTL，原子过期 |
| `sms:reg:resend:{phone}` | String `1` | `resend-interval-seconds`（60s）/ 失败时 `failure-cooldown-seconds`（10s） | 重发/失败冷却锁，`SET NX` 原子抢占 |
| `sms:reg:daily:phone:{phone}:{yyyyMMdd}` | 计数器 | 至当日 24:00（Asia/Shanghai） | 单手机号当日发送上限（默认 10） |
| `sms:reg:daily:ip:{ip}:{yyyyMMdd}` | 计数器 | 至当日 24:00（Asia/Shanghai） | 单 IP 当日发送上限（默认 30） |
| `sms:reg:global:{yyyyMMddHHmm}` | 计数器 | 120s | 全局每分钟发送总量熔断（保护账单/配额） |
| `sms:reg:verifyfail:{phone}` | 计数器 | 短窗口（如 60s） | verify 失败速率限制，防暴力枚举 |

实现要点：
- **所有"检查+占用"合并为单个原子操作**（Lua 脚本）：`INCR` 后立即用返回值判断是否超限，超限则不发并 `DECR` 回退；`INCR` 返回 1 时在同一脚本内 `EXPIRE`，避免"永久 key"与 check-then-act 竞态。
- 日计数 key 名的 `yyyyMMdd` 与"距当日结束"的 TTL **必须用同一时区**（统一固定 `Asia/Shanghai`，所有实例强制一致），避免跨天/多时区错位被卡边界翻倍。临近 24:00 的塌缩窗口列为已知小风险（可接受）。
- 写码/计数/attempts 自增全部原子（`HSET`+`EXPIRE` 同脚本、`HINCRBY`、`INCR`）。
- `InMemoryVerificationCodeStore` 用 `ConcurrentHashMap` + 过期时间戳 + 同等的"原子检查占用"语义模拟，供单测。

## 6. 防刷设计（多维限流）

发送前，按"原子占位"顺序检查，命中任一即拒绝（429）：

1. **同号间隔锁**（默认 60s）：`SET resend NX EX`，抢占失败即拒。
2. **单手机号日上限**（默认 10/天）：原子 INCR+判断+回退。
3. **单 IP 日上限**（默认 30/天）：同上。
4. **全局每分钟总量熔断**（新增，默认如 200/分钟，按账单容量设定）：最终保护阿里云配额/账单，挡住"多号×多 IP 矩阵"线性放大。
5. **复用现有 IP/分钟级限流**：将 `/api/v1/auth/send-register-code` 加入 `LoginRateLimitFilter.AUTH_PATHS`（硬编码 Set，改源码加一行精确 URI；阈值 `MAX_ATTEMPTS=5` 硬编码）。注意该 filter 与上述 Redis 多维限流是**两套独立计数、不共享**。

**客户端 IP 来源**：IP 维度限流依赖真实客户端 IP。明确取 IP 策略——与 `LoginRateLimitFilter` 现有取 IP 方式保持一致；若部署在反向代理/LB 之后，需配置**可信代理**并按可信跳数解析 `X-Forwarded-For`，否则 XFF 可被伪造直接绕过 IP 限流（实现阶段确认现有取 IP 实现是否已处理，未处理则一并修正）。

不引入图形/滑块验证码（按已确认决策）。

## 7. 测试旁路（mock + 万能码）— 修订口径

配置开关 `mateclaw.sms.mock`，**默认 fail-safe = `false`**（见第 8 节 `${SMS_MOCK:false}`，"忘配=安全"）：

- **`mock=true`（本地开发/集成测试显式开启）**：
  - 装配 `MockSmsCodeSender`：不调用阿里云，仅**非生产**日志打印手机号与码（便于联调）。
  - `VerificationCodeService.verifyAndConsume` 在正常校验之外，**额外接受配置的 `universal-code`（默认 888888）**，用于 dev 联调与 `@SpringBootTest` 集成测试免发短信。
- **`mock=false`（生产）**：
  - 装配 `AliyunSmsCodeSender` 真实发送；`MockSmsCodeSender` 与万能码逻辑在装配层即不可达。
- **启动期硬校验 `SmsStartupValidator`**：当 active profile 含 `prod`（或显式生产标识）时，强制 `mock` 必须为 `false`，否则**启动失败（fast-fail）**；`mock=true` 时打印显著启动告警横幅。

> ⚠️ **重要修订**：原 spec 称"现有写死 888888 的注册单测无需改动即通过"——**该说法不成立**。`AuthServiceRegisterTest` / `AuthControllerRegisterTest` 是纯 Mockito 单测、无 Spring 上下文，看不到任何配置；`register()` 改为委托 `verificationCodeService.verify*()` 后，这些测试必须**新增 `@Mock VerificationCodeService` 并 stub**（否则编译可过但运行 NPE）。万能码属于 `VerificationCodeService` 内部逻辑，对这些**纯单测不可见、不起作用**；它只服务于本地联调与集成测试。测试改动见第 12 节。

## 10. 前端改造（Login.vue）

- **验证码输入框：只允许 6 位数字** —— `maxlength=6`，输入事件剥离非数字；提交前校验恰好 6 位数字。
- 新增"获取验证码"按钮：点击调 `POST /api/v1/auth/send-register-code`，成功后启动 **60s 倒计时**并禁用按钮。
- 移除 `code: '888888'` 默认值，并确保获取验证码流程把码回填到 `registerForm.code`——否则 `handleRegister` 第 202 行 `!registerForm.code` 守卫会让提交**静默不发请求**。
- 错误处理：限流 429 → toast 友好提示（含可重试时间）；发送失败 → 通用错误提示；已注册 → 引导去登录。

## 11. 错误处理

| 场景 | HTTP | 行为 |
|------|------|------|
| 手机号格式非法 | 400 | 复用现有异常体系（与注册同一 normalize+正则口径）返回 |
| 手机号已注册 | 409/400 | 引导去登录（残余枚举风险见第 13 节） |
| 重发间隔内 / 失败冷却内 / 各维度日上限 / 全局熔断 | 429 | 友好提示，含可重试时间 |
| 阿里云发送失败 | 502 | 记录 `Code/Message/bizId` 入日志；删码、回退日额度、改设失败冷却锁；返回通用错误 |
| 验证码错误 | 400 | 原子累加次数；超 `max-verify-attempts` 作废并提示重新获取 |
| 验证码过期/不存在 | 400 | "验证码已失效，请重新获取" |
| 启动校验失败（prod 且 mock=true，或 mock=false 但 AK/SK 为空） | — | **fast-fail 启动失败**，拒绝带病上线 |
| Redis 不可用 | 503 | **fail-close**：拒绝发送/校验（宁可不可用，不可不限流被轰炸） |

所有对外文案不泄露验证码与内部细节；阿里云原始错误码仅入日志且确认不含码。

## 12. 测试策略

- **`VerificationCodeService` 单测**（用 `InMemoryVerificationCodeStore` + **手动 `new SmsProperties()` 并 set 字段**，不依赖 profile）：
  - 生成码长度恰为 6、纯数字（含前导零）、用 `SecureRandom`。
  - 校验命中并一次性消费（消费后再校验失败）。
  - 过期后校验失败。
  - 错误次数原子累加，超上限作废；verify 失败速率限制生效。
  - 重发锁原子抢占；失败冷却锁；并发场景下不超发（关键：验证"先占位"杜绝并发绕过）。
  - 单号 / 单 IP 日上限、全局每分钟熔断生效；时区固定。
  - `mock=true` 时万能码通过；**`mock=false` 时万能码被拒**（防误配回归）。
- **`AliyunSmsCodeSender` 单测**：mock 阿里云 client，断言 `SignName=迪伍科技`、`TemplateCode=SMS_508735089`、`TemplateParam={"code":"..."}`、`PhoneNumbers` 正确；模拟 `body.code != "OK"` 时抛可识别异常。
- **`AuthServiceRegisterTest` 改动（必须）**：新增 `@Mock VerificationCodeService`；原 invalid/missing code 用例改为 stub `verify*()` 抛对应异常；补充"验证码失效 / 错误次数过多"分支。
- **`send-register-code` Controller 测试**：成功、限流 429、格式非法 400、已注册分支。
- （可选）**集成测试** `@SpringBootTest` + `mock=true`：用万能码走通"发码→注册"全链路，无需真实短信。

## 13. 安全设计小结

- **凭据**：AK/SK 仅环境变量，禁止入库；要求 RAM 子账号（仅 `dysmsapi:SendSms`）；dev/prod 不同子账号；用户已暴露的密钥需立即轮换。`mock=false` 且 AK/SK 为空 → 启动 fast-fail。
- **万能码 fail-safe**：默认 `mock=false`；装配层 + 启动校验双重保证生产不可达；CI 断言 `mock=false` 拒万能码。
- **验证码随机性**：强制 `SecureRandom`，避免 `Math.random()`/`java.util.Random` 可预测。
- **不泄露码**：响应不含码；mock 打印码仅限非生产且生产 profile 关闭该日志点；审计所有日志点不含真实码。
- **防枚举/轰炸**：原子"先占位"限流；verify 失败速率限制；全局每分钟熔断保账单。
- **Redis**：生产强制鉴权（`REDIS_PASSWORD` 必填）+ 网络隔离；不可用时 fail-close。
- **已接受残余风险**：注册端点固有的"手机号是否可注册"枚举，以限流 + 监控告警缓解；临近 24:00 的日计数塌缩窗口。

## 14. 不在本次范围（YAGNI）

- 工作区级独立短信账号/签名（当前全平台统一账号）。
- 图形/滑块验证码。
- 登录、找回密码等其他短信场景（仅做注册）。
- 短信发送审计持久化表（如需另立项）。

## 15. 验收标准

1. 生产配置（`mock=false`）下，注册页点击"获取验证码"能收到来自"迪伍科技"签名、模板 `SMS_508735089` 的 6 位数字短信。
2. 输入正确验证码可注册成功；错误/过期/超次数/已注册按第 11 节返回对应错误。
3. 同号间隔内重发被拒；单号/单 IP 日上限、全局每分钟熔断生效；并发请求不超发。
4. dev/集成（`mock=true`）下不真实发短信；现有测试经第 12 节改动后全绿。
5. 仓库内无任何明文 AccessKey/Secret；凭据全部来自环境变量。
6. prod 且 mock=true，或 mock=false 但密钥为空时，应用启动 fast-fail。
